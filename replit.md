# CareMetric AI Intelligence

## Overview
CareMetric AI Intelligence is a React/Vite frontend application designed for healthcare provider intelligence, CRM, and analytics. It serves as a comprehensive data platform enabling provider management, lead generation, email campaigns, CMS analytics, and AI-driven insights to enhance healthcare provider strategies and outreach. The project's vision is to streamline healthcare data analysis and provider engagement, offering a robust toolset for market advantage and operational efficiency.

## User Preferences
The user prefers detailed explanations of changes and functionality. The user wants the agent to ask for confirmation before implementing major architectural changes or deleting significant portions of code. The user prefers iterative development with regular updates on progress. The user wants the agent to adhere to the established dark theme guidelines and responsive design patterns.

## System Architecture
The application is built with a React 18 + Vite 6 frontend, styled using TailwindCSS and Radix UI components, specifically leveraging `shadcn/ui`. State management is handled by TanStack React Query, and routing uses React Router v7. The backend is an Express.js API (port 3001) providing generic entity CRUD operations. Data persistence is managed by PostgreSQL with Drizzle ORM, encompassing 52 distinct tables. Authentication is JWT-based, utilizing bcrypt for password hashing. The system integrates AI capabilities via Anthropic Claude, email services through SendGrid, and file uploads via Multer. Frontend API client (`src/api/client.js`, re-exported as `base44` from `src/api/base44Client.js`) mirrors the Base44 SDK interface for consistent interaction with backend entities, integrations, and functions. In development, Vite (port 5000) proxies `/api` to the Express server; the frontend always talks to the same-origin `/api`.

The system spans three layers: (1) the **React SPA** (`src/`), with pages auto-registered in `src/pages.config.js`; (2) the **Express API** (`server/`); and (3) a layer of **Base44 Deno edge functions** (`base44/functions/`) that handle scheduled imports, maintenance fan-out, and import lifecycle hooks on the Base44 platform.

**Key UI/UX decisions include:**
- **Dark Theme:** Strict adherence to a dark theme palette: `text-slate-300/400`, `bg-slate-800/900`. Accent colors use `bg-*-900/30 text-*-400 border-*-500/30`.
- **Responsive Design:** Page wrappers utilize `p-4 sm:p-6 lg:p-8 max-w-[1400px] mx-auto`, with grids collapsing on smaller screens and tables supporting horizontal overflow.
- **Accessibility:** The shell has a skip link, `main`/`nav` landmarks, an `inert` collapsed sidebar and Escape-to-close on mobile; global search is a combobox with a listbox of results. Every control is labelled and icon buttons are named; jsx-a11y (lint), `tests/a11yStatic.test.ts` and axe (`tests/a11y.test.jsx`) enforce it. Contrast targets WCAG AA on the dark theme: text slate-400 or lighter, accent text -400, white text only on fills dark enough for it (-700 for cyan/teal/emerald/green).
- **Help:** `src/pages/Help.jsx` (`GUIDE_SECTIONS`) is the in-app guide and PDF. Each topic names its page and links there for people who may open it; search opens the matching topics. `artifacts/help/caremetric-intel-guide-sections.json` is a generated inventory of the guide (regenerate with `SOURCE_COMMIT=… node scripts/generate-help-inventory.mjs`; `tests/helpInventory.test.ts` checks it).

**Core Technical Implementations and Features:**
- **Provider Management:** Comprehensive tools for managing providers, locations, and territory mapping.
- **Facility Pages:** One list page, `Facilities.jsx` (`?type=hospital|home_health|hospice|snf|irf|ltch|dme|community_health`), serves 8 facility groups: Hospitals, Home Health, Hospice, SNF, IRF, LTCH, DME, Community Health (combined FQHC + RHC), with search and a state filter, plus a detail page consolidating all imported CMS data per facility. The old per-type pages (`/Hospitals`, `/HomeHealthAgencies`, …) redirect to it, keeping their query string. Backend: `server/functions/facilityDetail.ts` (getFacilityDetail, listFacilities, handleGetProviderCMSData). Pages: `Facilities.jsx`, `FacilityDetail.jsx`, and the DME report (`DMEProviderReport.jsx`, a tab of Facilities). **FacilityDetail** shows all raw_data columns (searchable, expandable table), 6 KPI summary cards, and a rich Provider Intelligence card (email, phone, lead score, taxonomies, status, "Full Provider Profile" CTA) when the facility provider_id matches a known NPI. **ProviderDetail** uses `base44.functions.invoke('getProviderCMSData')` for CMS data (not raw fetch), and shows LinkedFacilitiesCard on the Overview tab for quick facility cross-reference. LinkedFacilitiesCard handles all 8 facility groups for navigation. DB indexes: `idx_medfac_type_name`, `idx_medfac_provider_id`, `idx_medfac_type_state`. Listing queries use a single "primary type" per group for performance; `community_health` queries both `fqhc_enrollments` and `rural_health_clinic_enrollments`.
- **Provider CMS Data:** `handleGetProviderCMSData` returns MIPS, clinician profile, group practice, physician utilization, Part D prescribing, DME referrals, drug spending, facility affiliations, telehealth trends, and ACO network data. Data is grouped into `clinician`, `utilization_cms`, and `network` (ACO) categories. Displayed via `MIPSPerformanceCard` and `ProviderCMSDataCard` on ProviderDetail's Clinical and Network tabs. ACO data (participants, organizations, financial results) appears in a dedicated network section. `cmsImportTypes.js` contains labels for all 90+ configured dataset types. FACILITY_TYPE_GROUPS maps ~65 dataset types to 8 facility groups, ensuring all quality, payment, staffing, ownership, and VBP data flows into the correct facility detail page.
- **Sales & Outreach:** Functionality for lead lists, provider intelligence, and multi-channel campaigns.
- **Analytics:** CMS data analysis, network insights, and custom reporting capabilities, including materialized views for performance.
- **AI Assistant & Enrichment:** AI-powered tools for data enrichment and insights.
- **Data Import System:** Robust import mechanisms for Medicare/CMS datasets, NPPES flat files, and ZIP imports with pause/resume, error handling, and stall detection. **DataCenter** (`DataCenter.jsx`) is the import entry point with 9 category cards (Provider Data, Claims & Utilization, Hospitals & Quality, Home Health, Hospice, SNF & Nursing Homes, IRF/LTCH/DME, Enrollment & Market, Drug Spending) covering 90+ dataset types. `DataDestinationMap.jsx` maps every import type to its "View Data" destination page (facility group pages, Utilization, Providers, Organizations, CMSAnalytics, etc.) for post-import navigation. `ImportCategoryCards.jsx` defines the importable categories. `ImportMonitoring.jsx` provides real-time monitoring with 9 tabs (Monitor, History, Rules, Alerts, AI, AI Manager, Performance, Health, Automation), kept in `?importsTab=`.
- **Navigation:** `src/components/layout/navConfig.js` drives the sidebar (5 sections, 23 entries; regular users see 14), page access (default-deny; unlisted pages are admin-only) and highlighting. Related pages share one sidebar entry and a tab strip (`PAGE_GROUPS`, `PageTabs`): Facilities + DME report, Territory + County, Data Center + Dataset catalog + Import monitor, NPPES Crawler + Settings, Admin Settings + Scoring rules + Security audit. Old URLs in `LEGACY_REDIRECTS` (the eight facility pages, `OrganizationDetail` → `ProviderDetail`, `Campaigns` → `ProviderOutreach`, `EmailSearchBot`/`EnrichmentHub` → `ProviderIntelligence?tab=`) redirect with their query string; tests fail on orphan pages, missing targets, or a redirect that shadows a real page.
- **Operations alerts:** `server/lib/operationsAlerts.ts` evaluates a snapshot of `dataset_versions`, `import_schedule_configs`, the last `maintenance_fanout` heartbeat and `rollup_runs` into alerts (dataset behind a newer release ≥ 7 days, dataset left "importing" ≥ 6 h whose batch ended or went silent, schedule with ≥ 3 consecutive failures, heartbeat older than 2 h or with failing workers, rollup without a success in 2 days — 9 for the weekly `lead_scores` job). The `operationsAlerts` fan-out worker emails platform admins (the admin role or the flag, + `OPERATIONS_ALERT_EMAILS`) a digest at most once a day while anything is open and records an `operations_alert` audit event only once somebody received it (the throttle check, the send and the record run in one transaction under an advisory lock, so overlapping fan-outs send one digest); `getOperationsAlerts` (platform admins) feeds the Health tab's "Needs attention" list. A source that can't be read fails the worker and the list shows an error: only a table that doesn't exist yet (SQLSTATE 42P01) reads as empty. The fan-out starts every worker at once, so this one judges what earlier ticks left.
- **Organizations (multi-tenant):** Migration 0020 adds `organizations`, `organization_members` (`org_role` owner|member), `plans` and `org_usage`, and an `org_id` on every customer-owned table (lead lists, saved filters, reports, schedules, dashboards, scoring rules, campaigns, templates, tasks, alerts, audit events, assistant data); existing rows were folded into organization 1 ("CareMetric (legacy)") and every admin became a platform admin (`users.is_platform_admin`). Signup creates an organization in trial with the signer as owner (`server/lib/orgs.ts`) and records `terms_accepted_at`/`terms_version`. The session principal carries `orgId`, `orgRole`, `isPlatformAdmin`, `orgStatus`, `planCode` and `territory` (`server/lib/sessionUsers.ts`), so `server/routes/entities.ts` scopes reads and writes by `org_id` (`ORG_SCOPED_ENTITIES`) and stamps it on create; `adminOnly` means an organization's owner (`isOrgAdmin`), `platformAdminOnly` the platform (the `admin` role or the flag: `server/lib/roles.ts`); the function dispatcher uses `isFunctionAllowedFor` (`PUBLIC_FUNCTIONS` for all, `OWNER_FUNCTIONS`, a positive list of the campaign functions, for owners, everything else for platform admins only). `/api/admin/users` is org-scoped for owners (invites check the seat limit; the platform-wide admin role is platform-admin-only). Territory entitlements (`server/lib/entitlements.ts`, `assertTerritory` → 403 `outside_territory`, 402 `subscription_inactive`) guard the county, market, territory and referral-source functions; `server/lib/orgQuota.ts` counts AI calls, exports and outreach emails per day in `org_usage` (429 `quota_exceeded`). Billing: `server/lib/billing.ts` + `server/routes/billing.ts` (plans, status, Stripe Checkout, portal, territory, export counter) and the Stripe webhook in `server/routes/webhooks.ts` (`applyStripeEvent`); the Billing page is an Admin Settings tab for owners (one subscription per organization; a plan change updates it in place) and the sidebar widget shows plan status and AI usage. Frontend roles come from `effectiveRole(user)` in `navConfig.js`: `admin` (platform), `owner`, `user`. Public legal pages: `/terms`, `/privacy`, `/data-use` (`src/components/auth/LegalPages.jsx`); exports carry a source line.
- **Accounts:** Signup creates a `pending` account that can only see an "awaiting approval" screen until an admin approves it (Admin Settings → Users, backed by `/api/admin/users`). Admins can invite people (7-day single-use link), approve, change roles, disable/enable, issue 24-hour reset links, sign an account out everywhere, and delete never-approved accounts; they can't act on themselves or remove the last active admin. Users can change their password and sign out of every device from the sidebar's Account dialog, and request an emailed 1-hour reset link when SendGrid and `PUBLIC_APP_URL` are set. Sessions are an httpOnly cookie holding `{id, tv}`; role, status and `token_version` are read live per request (30s cache), so changes apply without re-login. Account events go to `audit_events` (`event_type='account'`). `scripts/admin-recover.ts` restores admin access from a shell. `MAIL_TRANSPORT=outbox` writes emails to a local JSONL file in development.
- **Security:** JWT-based authentication with role-based access control (adminOnly middleware), sensitive field stripping, and file upload size limits. User entity is explicitly excluded from generic CRUD for security. **Production secrets required:** `JWT_SECRET` (server hard-fails on startup if missing in production); `ADMIN_EMAIL` + `ADMIN_PASSWORD` (used to seed the first admin — production skips seeding with a warning if `ADMIN_PASSWORD` is unset; dev falls back to built-in defaults). **Entity router ACL:** sensitive entities (`ReconciliationSettings`, `ApiInteractionLog`, `NPPESCrawlerConfig`, `CMSApiConnector`, `ImportScheduleConfig`, `AuditEvent`, `ErrorReport`, `BackgroundTask`, `ImportBatch`, `ImportValidationRule`, `DataCleaningRule`, `ColumnMappingRule`, `ReconciliationJob`, `ProviderReconciliation`, `NPPESQueueItem`) are admin-only for both read and write. A whitelist of collaborative entities (lead lists, campaigns, scoring rules, custom reports, saved filters, etc.) allows non-admin writes; everything else requires admin. Internal DB error messages are no longer leaked to clients in production. ID parameters use strict integer validation (`/^-?\d+$/` + `Number.isSafeInteger`).
- **NPPES Crawler:** A dedicated crawler for the NPPES registry with actions for status, batch control, and queue processing.
- **Email Search Bot:** An AI-powered bot (Claude-based) for email discovery, validation, and automated saving to provider records. **Optimized for throughput:** single combined Claude API call (search + validate in one prompt, was 2 calls), 5 concurrent worker threads per batch, 300ms inter-provider delay (was 1500ms), default batch size 10. `providerIntelligenceBot.ts` also uses 5 concurrent workers and 300ms delay. Auto-resumes on server restart: if a task was in "processing" status, it resumes it; if the last task was "failed" (e.g. from a crash), it auto-starts a new task as long as unsearched providers remain and the last task wasn't explicitly cancelled. Batch size is always clamped to [1, 50]. Multiple orphaned "processing" tasks are reconciled (one resumed, extras marked failed). Workers check for cancellation every 10 providers for responsive stop behavior.
- **Data Quality Scan:** Utilizes sampling for performance, runs 13 quality rules, and generates alerts with Claude AI integration for analysis and fixes.
- **Backend Functions:** The Express function dispatcher (`server/routes/functions.ts`) exposes 75 functions, including optimized dashboard statistics, data health metrics, CMS dataset catalog, CMS analytics, referral network data, territory data, facility/provider detail, county intelligence, comprehensive reports, import triggers, NPPES crawler control, email/intel/enrichment bots, and campaign tooling. **Authorization is default-deny:** a `PUBLIC_FUNCTIONS` allowlist (read-only/analytics/status functions) is callable by any authenticated user; every other function (imports, crawler control, token-spending AI enrichment, email sending, destructive maintenance) is admin-only. Adding a new function is therefore an explicit security decision. **Dashboard stats** (`getDashboardStats`) uses raw pool connection with `SET statement_timeout = '5s'`, `pg_class` estimates for total counts, and `LIMIT`-based sampling (2000 providers, 10000 locations) for email/phone stats — extrapolated to full scale. Results cached 5 minutes. Responds in ~400ms cold, ~60ms cached. **Referral network** (`getReferralNetworkData`, `server/functions/referralNetwork.ts`) builds the graph from `cms_referrals` provider pairs for a state, a lead list, one provider's partners, or a labelled nationwide sample, using index-backed `IN` queries only (never a scan or `GROUP BY`). It returns the busiest providers (default 150, max 300) with real edges between them, per-provider volumes, partner counts, PageRank-based hub scores and a whole-network summary; cached 10 minutes per scope, 20 uncached builds per user per minute. Specialties are grouped by NUCC taxonomy code (`server/lib/specialtyGroups.ts`, mirrored in `src/lib/specialtyGroups.js`). **Search** (`searchProviders`, `searchLocations` in `server/functions/search.ts`): people by last-name prefix ("Smith", "John Smith", "Smith, John"), organizations by any part of the name via `pg_trgm` (prefix only if the extension is unavailable), NPIs exactly or by prefix, and locations by NPI, ZIP/ZIP+4, "City, ST" or state; a city without a state asks for one rather than scanning. Each match kind is its own index-backed query (expression indexes built at boot from `server/lib/searchIndexes.ts`), merged and ranked in JS; a state filter is applied to a bounded candidate list. While an index is still building, results are flagged `degraded`. **Rollups:** analytics that need a whole big table (ZIP location density, Medicare utilization by service type, most-referred-to providers, facility dataset counts) are computed in the background by `server/lib/rollups`: primary-key chunks of 100k rows under a 30s statement timeout each, accumulated in memory, then the `rollup_*` table and its `rollup_runs` row are replaced in one transaction under a per-job advisory lock. The `refreshRollups` maintenance worker queues jobs that haven't succeeded in a day (one at a time); admins can force a refresh from CMS Analytics. `getCMSAnalytics` reads only the rollups and reports when each section was computed. **Market rollups** (`server/lib/rollups/market.ts`, migration 0018) are query-kind jobs: one SELECT each over the typed CMS tables and the Census geography fills `rollup_hospital_catchment`, `rollup_county_hospital_sources`, `rollup_hospital_discharge_mix`, `rollup_pac_market_share`, `rollup_agency_coverage`, `rollup_referral_sources` and `rollup_county_market_profile`. `server/functions/market.ts` serves them (`getCountyMarket`, `getHospitalCatchment`, `getFacilityMarket`, `getCountyMarketLayer`, `getReferralSources`, `getServiceAreaOverlap`, all public read-only) to County Intel's Market / Hospital sources / Competitors / Referral sources tabs, the `MarketIntelligence` county table (a Territory group tab), the Territory map's county layer, hospital and post-acute facility pages and the provider Referral Potential card; the assistant's `get_area_summary` carries a `market` block. **Geography:** 2020 Census counties, ZCTA centroids and ZCTA-to-county land shares are bundled in `server/data/census` (about 0.8 MB, public domain, checksummed by `manifest.json`), loaded into `geo_counties` / `geo_zctas` / `geo_zcta_counties` at boot (or `npm run geo:load`; `GEO_AUTOLOAD=false` to skip) and served from memory by `server/lib/geo.ts`. `getGeoCounties` and `getGeoStatus` are public; `loadCensusGeography` is admin-only. **NUCC taxonomy:** the Health Care Provider Taxonomy code set (about 880 codes) is bundled the same way in `server/data/nucc` (`scripts/nucc/build-nucc-taxonomy.ts`, checksummed), loaded into `nucc_taxonomies` at boot (`npm run nucc:load` to force) and served from memory by `server/lib/taxonomy.ts`; the NPPES file importer uses it to describe taxonomy codes and logs codes the bundled version doesn't know. `getDataFreshness` reports the loaded version alongside the Census vintage. **Census ACS demographics:** the 5-year estimates for counties and ZCTAs (population 65+/85+, 65+ living alone, median income and home value; `scripts/census/build-acs.ts`, bundled under `server/data/census` with `acs.manifest.json`, loaded at boot by `server/lib/census/acs.ts` into `census_acs_county` / `census_acs_zcta`, `npm run acs:load` to force) feed the county market profile. **Licensed facilities:** `licensed_facilities` (migration 0019) holds state-licensed personal care and assisted living homes imported from CSV uploads (typed route `licensed_facilities`; state and license type from the import's parameters when the file lacks them; county from the ZIP); they list on Facilities › Licensed Homes, on County Intel's Competitors tab, and as homes/beds in the county profile. Nursing-home census and payer mix (CMS-671) show on SNF facility pages and competitor rows. Caveats: 2020 vintage, ZIPs that aren't ZCTAs fall back to the ZIP3 area or the state, about 200 tiny ZCTAs without relationship rows take their nearest neighbour's county, and the territories' county equivalents (which the county Gazetteer lacks) are included when they are some ZCTA's main county, placed at those ZCTAs.
- **Base44 Edge Functions & Scheduled Maintenance:** `base44/functions/` holds 26 Base44 **Deno** edge functions (importers, hooks, workers, AI helpers) that run on the Base44 platform — distinct from the Express backend. The Deno `runScheduledImports` is legacy: the cron driver is the Express endpoint `POST /api/maintenance/runScheduledImports` (`server/functions/scheduledImports.ts`), which claims due `import_schedule_configs` rows (lease-based), starts them, marks each schedule `running` with its `last_batch_id`, and then runs the one maintenance fan-out in `server/lib/maintenance.ts` (`FANOUT_WORKERS`: `settleScheduledImports`, `checkCmsCatalog`, `autoResumePausedImports`, `autoRetryFailedImports`, `manageCrawlerRetries`, `cancelStalledImports`, `runDueScheduledReports`, `refreshRollups`, `refreshLeadScores`). A schedule succeeds only when its batch completes (`server/lib/importCompletion.ts`). `dataset_versions` records which version of each CMS dataset is loaded and what the CMS catalogs list as current (`server/lib/cmsCatalog.ts`, `server/lib/datasetRegistry.ts`); `getDataFreshness` shows it in the footer, the dataset catalog and Help. Hosts without a cron can set `MAINTENANCE_INPROCESS_INTERVAL_MS`. Each worker is idempotent and self-throttling. Import lifecycle hooks (`onImportBatchCompleted`, `onImportBatchFailed`, `onRuleCreated`) and per-state NPPES supervision (`superviseNPPESCrawler`) also live here. Pure scheduling/retry logic is factored into `helpers.ts` per function so it can be unit-tested from Node without booting Deno.
- **Auto-Retry & Import Health:** Failed import batches whose error is transient are retried automatically. `autoRetryFailedImports/helpers.ts` classifies retryable errors (network/HTTP 5xx/429/rate-limit/connection keywords), tracks attempt counts (capped at `MAX_AUTO_RETRY_ATTEMPTS`), and schedules the next attempt with exponential backoff (capped at `RETRY_BACKOFF_CAP_HOURS`). The frontend mirrors this logic in `src/components/imports/retryStatus.js` and computes health rollups in `healthMetrics.js` (success-rate-by-day, top error categories, retry-pipeline buckets, unhealthy schedules). `MaintenanceHealthPanel.jsx` (embedded in `ImportMonitoring.jsx`) polls the latest `maintenance_fanout` `AuditEvent` heartbeat and warns when maintenance is stale, partial, or the cron is unwired. `ImportHealthDashboard.jsx` renders the 30-day outcome chart, error breakdown, retry pipeline, and schedule-health table.
- **Territory & County Intelligence:** `TerritoryIntelligence.jsx` and `CountyIntelligence.jsx` keep their filters in the URL (`useUrlState`), so a view can be shared and Back restores it. **Territory** (`getTerritoryData`, `server/functions/territory.ts`): the state list comes from `pg_stats` most-common values × `reltuples` (labelled approximate, no scan); the sample is the state's highest lead scores first (keyset-walked on boot index `idx_lead_scores_score_id`), then other Practice locations, or a specialty group via `searchBySpecialty` (a practice location in the state and the entity filter apply while choosing, before the limit); scores are `lead_scores`, then `ai_outreach_score`, else "Unscored" (`null`, never 0); positions come from `geo.coordsFor` (ZCTA centroid → ZIP3 → state, with a deterministic jitter) and counties from ZCTA land share; county density reads the ZIP rollup. Cached 5 minutes per scope. **County** (`getCountyIntelligence`, `server/functions/countyIntelligence.ts`): takes `{state, county_fips}` (a legacy county name goes through `resolveCounty`), turns the county into its ZCTAs (land share ≥ 0.5) and queries `left(zip,5) = ANY(...)` with bounded samples (5,000 locations, 1,000 provider details; the provider list holds the 200 highest scored and the page says when it's capped); above the sample the page shows the ZIP rollup's practice-location count ("≈", a provider with several locations counts more than once) instead of a provider count. Facilities come from the imported Medicare facility datasets (`LISTING_PRIMARY_TYPES` + `getFacilityTypeGroup`), referrals skip NULL targets and carry names, and top services are grouped by HCPCS code. `getZipCoordinates` (≤ 2,000 points) and `getGeoContext` (a ZIP's county and rollup counts) are public and back the Providers map and the provider page's territory card. Nav entries: "Territory" and "County Intel" in Analytics.
- **Comprehensive Report:** `ComprehensiveReport.jsx` — lazy-loaded, printable, collapsible sections showing all provider data (locations, taxonomies, utilization, referrals, affiliations, lead scores, enrichments). Backend: `server/functions/comprehensiveReport.ts` uses single pooled connection with `statement_timeout`. Integrated as "Full Report" tab (#7) in ProviderDetail and inline button in FacilityDetail.
- **Relationship Cards:** `ReferralPartnersCard.jsx` (sent/received tabs with bar charts) in ProviderDetail Network tab. `AffiliatedProvidersCard.jsx` (uses ProviderAffiliation entity) in FacilityDetail.
- **DB Performance Notes:** `provider_locations` (12M rows), `providers` (6M rows), `medicare_facilities` (46M rows). Avoid DISTINCT/GROUP BY on provider_locations or full-table scans on medicare_facilities without proper indexes. The `medicare_facilities` table lacks a standalone `state` index (only has `(facility_type, state)` composite). Referrals table (`cms_referrals`) only has NPI index, not `referred_to_npi` index. Use IN-clause with pre-fetched NPI lists instead of JOINs/subqueries.

## External Dependencies

- **AI:** Anthropic Claude (via `/api/integrations/ai/invoke`). Models centralized in `server/lib/aiModels.ts`: **Sonnet 4.6** (`claude-sonnet-4-6`) for conversational assistants, multi-step reasoning, and analytical/structured output (Data Quality Assistant, Pattern Analysis, AI Import Manager chat, default `/ai/invoke`); **Haiku 4.5** (`claude-haiku-4-5-20251001`) for high-volume bulk worker loops (Email Search Bot, Provider Intelligence Bot, third-party enrichment, custom data-point lookup); **Opus 4.7** (`claude-opus-4-7`) reserved for the heaviest reasoning tasks. All models (including the assistant's, `CLAUDE_MODEL_ASSISTANT`) can be overridden via `CLAUDE_MODEL_SONNET` / `CLAUDE_MODEL_HAIKU` / `CLAUDE_MODEL_OPUS` / `CLAUDE_MODEL_ASSISTANT` env vars without code changes. **AI Assistant** (`/AIAssistant`, `server/lib/assistant`, `server/routes/assistant.ts`): saved, owner-only conversations answered by `CLAUDE_MODELS.ASSISTANT` (its own default in `aiModels.ts`, overridable with `CLAUDE_MODEL_ASSISTANT`; effort `ASSISTANT_EFFORT`, default medium) over a streaming tool loop sent to the browser as server-sent events. Tools (zod-validated, results capped at 12k characters): `search_providers`, `get_provider_profile`, `get_area_summary` (County/Territory handlers), `get_referral_network`, `get_dashboard_stats`, `list_lead_lists`, `get_lead_list`, and `propose_lead_list`, which only records a proposal; the list is created in one transaction when the user presses Create list on the card (single-use, owner-checked, 24h expiry, audited), and the model is told what the user decided on the next turn through a system message. Requests use adaptive thinking with progress notes (`display: "updates"`), top-level prompt caching, server-side refusal fallback (`fallbacks: "default"`) and `drop_block` for thinking blocks whose prefix changed (e.g. after a deploy edits the prompt). Every API message is stored verbatim and append-only in `assistant_messages`; only complete turns are replayed, so stopped, refused or failed turns stay visible but don't affect later answers. Limits: at most 8 tool rounds and 90s of model calls per answer (then it must answer), one answer at a time per conversation, `ASSISTANT_REQUESTS_PER_MINUTE` (6) questions a minute and `ASSISTANT_DAILY_TOKEN_BUDGET` (1M units) a day per user, `ASSISTANT_MAX_TURNS` (40) questions per conversation; 503 with a clear message when `ANTHROPIC_API_KEY` is unset. Answers render Markdown without images (a planted image URL could leak data) and show the host of outside links. Conversations are kept until their owner deletes them (no automatic retention yet).
- **Email:** SendGrid (via `/api/integrations/email/send`)
- **Database:** PostgreSQL (with Drizzle ORM). Migrations are hand-written SQL in `./drizzle/`, listed in `drizzle/meta/_journal.json` with strictly increasing `when` values, and written idempotently (`IF NOT EXISTS`). `npm run db:migrate` (`server/db/migrate.ts`) applies them under an advisory lock; a database that was only ever built with `db:push` is baselined automatically (0000 recorded as applied when every table it creates that `schema.ts` still defines exists, 0002 when its table does; a database with only some of 0000's tables stops with an error naming the missing ones). The Replit post-merge hook runs `db:migrate` and fails if it fails; deployments can set `DB_MIGRATE_ON_BOOT=true` to migrate before the server listens. Don't use `db:push` on shared or production databases: the large-table indexes built at boot (`server/lib/bootIndexes.ts`) aren't in `schema.ts`, so push drops them. `npm run db:status` lists pending migrations; `npm run db:seed-demo` loads synthetic data into a local database.
- **File Upload:** Multer (for `/api/integrations/file/upload`)
- **Edge Runtime:** Base44 platform (Deno) for `base44/functions/` — uses `npm:@base44/sdk` and `npm:`-prefixed imports; not part of the Node/Express runtime.
- **Testing:** Vitest + React Testing Library + jsdom (dev dependencies); CI via GitHub Actions.
